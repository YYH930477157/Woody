# 工作流角色模板

新建团队时，可选择工作流模板和一个基础助手。选择模板仅预览流程；点击“确认创建”才会创建角色副本、保存角色规则并创建团队。

| 模板       | 阶段                                                            |
| ---------- | --------------------------------------------------------------- |
| 新功能开发 | 需求分析 → 方案设计 → 代码实施 → 测试验证 → 代码审查 → 交付汇总 |
| 缺陷修复   | 需求分析 → 代码实施 → 测试验证 → 代码审查 → 交付汇总            |
| 代码审查   | 需求分析 → 代码审查 → 交付汇总                                  |

首个角色兼任队长。创建团队本身不会发送任务或调用模型。

## 队长如何推进

- 接到目标后，队长先自己完成需求分析，把范围、验收标准、不做的事和待确认问题交给用户确认，等用户确认后才进入下一环节；用户明确说“不用确认直接做”时跳过。代码审查模板只在审查对象或范围不清时才停下来问。
- 一次只派一个环节。上一环节的交接消息到达后，队长才为下一环节创建任务，并把完整交接写进任务描述。
- 不预先建好后续环节的任务，也不用任务依赖串联环节。原因：Team 引擎在上游任务标记完成时会立即唤醒下游负责人，而成员是先标完成、再发汇报，预建的下游任务会在交接到达前就开始。
- 测试或审查要求返工时，队长新建带有问题清单的实施任务，再新建复测、复审任务，最多两轮后报告剩余阻塞。审查模板不进入实施。
- 团队成员已齐全，队长不再提议或创建额外队员，除非用户要求。

每个角色的交接都要包含：环节、状态（passed / blocked / changes_requested）、输入、产物路径或完整摘要、验证证据、未解决问题和下一负责人。会话 ID 本身不代替交接信息。修复流程要求先复现问题。

## 配置与持久化

- 每次创建使用独立、可编辑的用户助手副本，不修改基础助手。副本使用“团队名 · 角色名”命名，在助手设置中管理。
- 副本继承基础助手的引擎、解析后的默认模型、规则，以及它作为团队成员实际会带上的技能、MCP 工具、权限和思考强度，均以“固定”方式写入。原因：团队成员会话不接收单次对话的覆盖设置，“自动”模式取的是该助手自己的上次使用记录，新副本没有记录，否则会丢失基础助手的工具和技能。之后再修改基础助手不会影响已创建的副本。
- 选择适合代码工作的基础助手，避免与角色职责冲突的原有规则。
- 规则使用无语言后缀的存储方式，切换界面语言仍能读取。角色约定要求使用用户语言回复。
- 角色准备失败会尝试删除本次新建的副本；清理失败会显示剩余 ID。未创建团队前不会返回不完整的角色列表。
- 团队创建失败后，保持弹窗并重试可复用已准备的角色；关闭弹窗会删除这些尚未用于团队的副本。

## 能力边界

这是基于角色指令和现有 Team 任务、消息能力的协调模板。需求确认、阶段顺序、返工次数、角色职责由模型遵守，尚无引擎强制门禁、持久化阶段状态机、断点恢复或可视化流程编辑器。角色约定不授予或限制工具权限，实际权限沿用现有运行时机制。提交、推送、合并、部署及外部消息仍需遵循用户授权。

团队成员会话目前不设置代码记忆（codebase memory）所需的工程路径，即使副本绑定了该 MCP 也无法查询代码图谱。

## 验证

单元测试覆盖角色模型配置继承、“自动”设置按基础助手实际值固定、规则保存、部分失败清理、清理失败提示、模板阶段、队长逐环节派发与需求确认规则和不可用助手。弹窗测试覆盖无副作用预览、来源助手选择和创建失败后的重试。真实后端冒烟使用独立临时数据目录验证规则跨语言读取与六成员团队创建；不发送模型任务。
