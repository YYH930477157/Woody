# 模块专家团队

按阶段分工的模板（需求 → 设计 → 实现 → 测试 → 评审 → 交付）让同一批角色轮流处理所有模块。固件项目的各个模块往往由不同的人写，逻辑和风格差别很大，更适合按模块分工：一个总管判断需求归谁，每个子模块一位专家长期负责，再由一位验证员检查合在一起的结果。

## 项目初始化：模块分类和模块简报

C/C++ 项目（以及已经有架构文件或 `experts.json` 的项目）在架构面板开启代码记忆后，每次索引成功，Woody 不用模型就写好以下内容。其他项目仍然要点按钮才生成。

- **架构文件** `.woody/architecture.md`：第一次索引就生成，标题文字用发起索引时界面的语言，之后保留文件原来的语言；同时覆盖任务、主/次调度表、指定字段与按位置初始化的结构体函数指针表、跨镜像接口向量表（如 `Boot` / `APP1` / `APP2`）以及大型数据表与 X-Macro 头文件。原来要点按钮才会生成，现在按钮只用于立即重写。
- **模块分类**：架构文件末尾的“模块分类”一节，架构面板的“模块与专家”区也会列出。在调度表、独立 RTOS 任务或被调用的结构体函数表里登记了入口的每个源文件（或同一目录下拆分成 `<模块>_*.c` 的一组文件，例如把 `display.c` 拆成多个 `display_*.c`）算一个模块，连同对应头文件（`<模块>.h` 和 `<模块>_*.h`），以及函数名前缀与它相同的其他源文件；跨模块共用的无主调度/表定义文件会提示为候选 `shared` 文件。一个前缀如果另有三个以上的源文件在用，说明它是整层共用的前缀，这些文件不并入；第三方库和示例目录里的文件也不并入。模块编号取模块名或文件名，同名时加上所在文件夹名。架构面板和建团弹窗把这类拆分模块存进 `experts.json` 时会自动写成 `<目录>/<模块>_*.c`（和 `<目录>/<模块>_*.h`）通配路径，后续新增同前缀拆分文件仍归该专家负责。只有分类判定为拆分模块的才这样写，而且通配路径不能匹配到别的模块的文件；只是第一个下划线前的前缀相同（比如 `drv_uart.c` 和 `drv_uart_dma.c`）的文件仍逐个列出。
- **专家卡片的事实部分**：`.woody/experts.json` 里的每位专家，在 `.woody/features/<编号>.md` 的 `woody:generated` 标记之间写一份模块简报，包括：
  - 负责的文件及其索引状态（列出索引里每个文件的函数名，多行初始化数据表及解析失败/纯表文件的顶层数据表行号目录，专家按名字比对，不比数量）：哪些行只解析了一部分、哪些文件整个解析失败、哪些文件在索引后改过（位置可能偏移）、磁盘上符合路径但尚未进入索引的文件，以及同一模块下新增但尚未纳入 `experts.json` 的未归属文件。
  - 本模块在哪个任务、哪张调度表（附顺序约束注释）或结构体函数表里，排第几项，在什么 `#if` 条件下生效；以及镜像间接口向量表（`Boot` / `APP1` / `APP2`）、RTOS 软定时器回调、中断/HAL 回调入口和入口函数的 1 层内部调用骨架。
  - 模块外调用本模块的位置（按不同专家均衡展示，并注明调用方属于哪位专家、共享文件或无主模块）；以及本模块调用了别的模块的哪些函数（超出条数时列出剩余目标模块及函数数，不静默丢弃）。
  - 本模块定义的全局变量及模块外写入、取地址（含数组指针传参）、读取它们的位置；以及本模块读写、取地址的其他文件全局变量（数据来源与外部状态变更）。全局变量从源码扫描（支持 `#if` 分支、`extern "C"` / `namespace`、函数指针数组和常见放置宏），使用位置靠全文搜索（含头文件内联/宏引用）。
  - 本模块在头文件和源文件中定义的核心数据结构（`struct`/`union`）、枚举（`enum`）、头文件内联函数与 X-Macro 表。
  - 名字含 `ADDR` 的地址宏及常见存储标识（`NVM_*`/`EEP_*`/`FLASH_*`/`PARA_ID_*` 等）及其全部 `#if` 定义分支、编译条件或枚举/X-Macro 定义位置（超出上限时列出余名）。
  - 编译开关（过滤 `ENABLE`/`ON`/`TRUE` 等常量值词，并从项目头文件解析当前生效 `#define` 值）。
  - “索引核对”：专家依赖索引之前，必须先到源码里核对的问题。

标记以外的内容属于专家和用户，Woody 不改。卡片原来没有标记时，生成区追加到文件末尾；卡片读不出明文时不覆盖，只在状态里记一条错误。

Woody 按专家负责文件的内容、模块边界/调度指纹和卡片标记以外（不含“用户更正”一节）的专家内容，判断卡片状态：用户在“用户更正”里补充记录不会把“未熟悉”或“需重新核对”误标为“已熟悉”。调度指纹只记名字：模块的任务名、登记它的调度表/结构体函数表/镜像间向量表项和 `#if` 条件、未归属的同模块文件、未索引磁盘文件、匹配不到文件的路径；不记行号和表里第几项，别的文件加一行或别的模块插一项都不会让卡片过期。升级前已熟悉、文件也没变的卡片，升级后仍是已熟悉。此外，卡片摘要还会提示专家手写部分缺失的关键模块章节。

| 状态       | 含义                                                                |
| ---------- | ------------------------------------------------------------------- |
| 未生成     | 还没写简报，或专家负责的文件清单改过                                |
| 未熟悉     | 标记以外还是空的                                                    |
| 已熟悉     | 专家写过卡片，此后负责的文件、同模块归属边界与调度表登记均无变化    |
| 需重新核对 | 专家最后一次写卡片之后，负责的文件改过，或模块发生拆分/调度登记变化 |
| 出错       | 卡片读不出或写不进                                                  |

架构面板的“模块与专家”区：

- 列出各位专家和卡片状态；点“更新卡片”，从当前索引重写所有简报。
- 勾选几个模块，点“设为新专家”：编号、名称和职责都预先填好，确认后写入 `experts.json`，并立即为这位专家写好简报。
- 也可以选一位已有专家，把勾选的模块并入它负责的文件。

## 内置模块专家

从 AionCore woody.14 起，助手列表里自带四位模块专家，与其他内置助手一样（不能删除，带头像、中英文名称和示例问题），默认启用：

| 专家     | 编号                   | 负责                                                                         |
| -------- | ---------------------- | ---------------------------------------------------------------------------- |
| 告警专家 | `woody-alarm-expert`   | 告警和篡改（防窃电）检测、阈值与延时参数、告警标志，事件代码、事件记录和计数 |
| 曲线专家 | `woody-profile-expert` | 负荷曲线的捕获、存储、读取、复位和协议对象，结算的触发、冻结和结算曲线       |
| 显示专家 | `woody-display-expert` | 显示列表、轮显与按键、显示格式、图标、段码屏驱动                             |
| 状态专家 | `woody-status-expert`  | 状态位定义、汇总、锁存与清除，状态接口                                       |

- 从 AionCore woody.18 起，告警专家也负责事件记录和防窃电，曲线专家也负责结算（结算日调度、冻结和结算曲线）。项目的 `experts.json` 把这些分给了别的专家时，以清单为准，那部分只是它们的接口。跨日、跨月等时间触发仍归时钟专家，触发后的结算动作归曲线专家。
- 归属按模块的职责判断，不按谁调用它。状态模块的文件整个归状态专家，包括汇总告警、篡改、时钟状态的代码；各模块都调用它的状态获取函数，并不会让它变成共享文件。`experts.json` 没列、但明显属于某位内置专家的文件，电表总管写成“建议归某专家（清单未列）”，并建议在架构面板里并入，不写成无人负责。
- 专家卡片“模块外的调用”先列被其他专家调用的函数，超出条数的也列出函数名；专家追踪链路时要查自己函数在模块外的全部调用方（时钟模块校时后调用调度补结算、状态模块查询篡改状态拼告警位，都是这样找到的）。
- 规则文件只写公开的通用电表知识，例如 DLMS/COSEM 曲线对象的属性、显示列表的常见做法，不含任何具体项目的内容。具体项目的细节，由专家用代码记忆学习后写进那个项目自己的卡片。
- 每位专家默认启用内置技能 `woody-module-expert`，并带上 `woody-codebase-memory`。项目开启了代码记忆时，Woody 会照常给对话加上代码记忆的工具。
- 开始时，专家按技能找到自己负责的文件。顺序是：团队任务指定的文件、`.woody/experts.json` 里对应编号的专家、`architecture.md` 的模块分类，都没有时按规则里列出的关键词搜索，并请用户确认。然后专家检查代码索引，读卡片；卡片缺失或过时时，建议先熟悉模块。

`woody-module-expert` 技能是这套做法的完整版：

- 找到自己的模块。
- 依赖索引之前先核对：`index_status`，`check_index_coverage` 里的部分解析、解析失败和索引后改过的文件，索引漏收的全局变量和间接调用；报索引问题必须附证据。
- 熟悉模块的步骤。
- 回答问题时给出证据。
- 负责任地修改：全项目找副本、跨模块先请对方评估、不替用户确认需求、编译、更新卡片。

模块专家团队里的专家角色也默认带上这个技能，规则里保留简短版本，作为 AionCore 较早版本没有这个技能时的后备。

## 新建团队

工作流模板选“模块专家”，再选基础助手和工作空间。弹窗读取工作空间的 `.woody/experts.json`，列出项目的专家：

- 每位专家有名称、编号、职责和负责的文件。编号用小写字母、数字和 `-`，也是功能卡片 `.woody/features/<编号>.md` 的文件名。负责的文件每行一个，相对项目文件夹；以 `/` 结尾的是文件夹，`*` 匹配一段路径里的任意字符；不能是绝对路径，也不能含 `..`。
- “共享文件”不归任何专家，比如任务表和公共头文件。每次由总管指定一位专家修改。
- 勾选这次加入团队的专家，默认全选。勾选不写回文件。
- 项目还没有 `experts.json` 时，按 `.woody/features` 里已有的功能卡片列出候选，名称先用卡片名，职责和文件待填。没有卡片但索引检测到了模块时，每个模块列成一位专家（最多 12 位），名称和职责与架构面板“新建专家”的草稿相同，文件取模块的文件，可以直接创建。都没有时列表为空，点“添加专家”逐个添加。
- 专家列表上方按索引状态显示提示：没开代码记忆、还没索引、正在索引、上次索引失败、源码在上次索引后有新增/修改/删除，并带一个按钮开启并建立或更新索引。索引完成后，用户没改过的专家列表按新索引重新列出，勾选保留。加密预检拒绝索引时，提示把索引程序加入白名单，按钮是“仍然建立索引”。
- 任何一位专家的信息不完整或与其他专家重名、重编号时，在该行提示原因，不能创建。最多 12 位专家。

项目开启了代码记忆时，每位专家的名称旁显示卡片状态（见上一节）。专家列表下方有一个勾选项“建团后让专家先熟悉模块”，默认勾选。

点击“确认创建”：

1. 专家清单有修改或项目还没有文件时，先写入 `.woody/experts.json`。写入失败则提示原因，不创建任何东西。已有文件读不出来（不是合法 JSON、超过 64 KB、加密电脑上 PowerShell 7 也读不出明文）时，提示原因，不覆盖它。
2. 项目开启了代码记忆时，先从当前索引补写缺失或过时的简报（从未写过，或专家负责的文件清单改过），再读取每位专家的卡片状态和简报摘要。没有可用索引时跳过这一步，团队照常创建，只是规则里没有简报。
3. 开启“独立工作区”时建 worktree（见 [独立工作区](isolated-workspace.md)）。
4. 以基础助手为模板创建角色副本：总管（队长）、所选专家、验证员，副本命名“团队名 · 角色名”。副本的设置方式与阶段模板相同，见 [工作流角色模板](workflow-presets.md)。
5. 创建团队。
6. 勾选了“建团后让专家先熟悉模块”时，Woody 给卡片不是“已熟悉”的每位专家发一条消息，让它先熟悉模块（没有代码记忆时所有专家都会收到）。消息发不出去时只提示，团队已经建好，不会撤销。

## 三类角色

**总管**的规则里有一张分派表：每位专家的名称、编号、职责和负责的文件，加上共享文件和验证员。文件归属的判定规则写在规则里：路径相同、在以 `/` 结尾的文件夹下、或被 `*` 模式匹配，多条匹配时取最长的那条。总管不改项目文件。收到需求后：

1. 读 `.woody/architecture.md` 和可能相关专家的功能卡片，用代码记忆（没有时用搜索）找到要改的代码，按分派表找到每个文件的负责人。
2. 把分派方案给用户确认：谁做什么、各自改哪些文件、模块之间的接口（函数、数据结构、NVM 地址、调用位置和顺序）、先后顺序、验证员检查什么。用户确认后才派发；用户改了方案要重新确认；用户明确说不用确认时跳过。只问某个模块、不需要改动的问题，直接交给该专家。
3. 用任务派发，任务描述里写完整交接，因为成员看不到总管和其他成员的对话。有接口依赖时先派提供方，拿到它的交接后再派使用方；只有文件不重叠、彼此不依赖时才同时派。不预建任务、不用任务依赖串联，原因同阶段模板。
4. 专家需要改别人的文件时，总管决定由谁改：负责的专家另开任务，共享文件或无人负责的文件指定一位专家。同一个文件不让两位专家同时改。
5. 所有专家交接到齐后，给验证员建一个任务，附上全部交接、改动文件和验收标准。验证员发现问题时，按文件归属交回对应专家，再重新验证；最多两轮，之后把剩余问题报告给用户。
6. 最后汇报：每个模块改了什么、验证证据、遗留问题、更新了哪些功能卡片。

总管出改动方案前，要自己用 `search_code` 搜每个要改的类型、字段、默认值、地址宏、协议编号和函数，或者请负责的专家列出清单，并把用到、构造或复制它们的每一处（初始化器、`sizeof`、`offsetof`、调用方）连同文件、行号和负责人写进方案，避免别处的副本被漏改。需求里的疑问列给用户，不把自己的理解当成已确认。一项改动如果新增了对别的模块的调用，或改变了别的模块依赖的数据、时序或行为，在派给验证员之前，先让那个模块的专家评估副作用并更新卡片；用户直接找专家提的改动也一样。专家报告卡在等决定时，总管立刻把问题、选项和副作用转给用户。

建团时勾选了“熟悉模块”的专家，名单写在总管的规则里：它们报到之前，总管不给它们派需要改代码的任务，只关于该模块的提问可以直接交给它们。专家报上来的索引问题和文件清单建议，由总管逐位专家原样转告用户，有专家报了问题时不能说索引正常；是否修改 `experts.json` 由用户决定。

需求不属于任何专家时，总管告诉用户，请用户指定人选或在 `.woody/experts.json` 里加一位专家，不自己动手。

需求以表格给出时（比如同时有“需求模版”和“需求”两列），总管用脚本按表头名把每一行打印成“表头名 = 值”，不按列号取值，输出乱码就算没读到。每个专家任务里写明按哪一列判断、哪一列只作差异说明、要核的行号，并附一行打印样例。实测中专家按位置读表，把模版列当成了项目要求。

汇报或出方案前，总管自己复核专家的“不满足”和数值差异：打开专家引用的行和背后的宏或默认值，在报告里给每条标“复核”（打开的 `path:line` 和看到的值）或“未复核”。团队队长的通用规则让队长把实现交给成员，规则里写明复核是总管自己的工作，不算交出去的实现工作；实测中没有这句时，总管只转述专家的结论。汇总行的条数要在逐条表格写完后按表格数出来：连续两次实测里，总管写的条数和表格对不上。

**专家**的规则里带有自己卡片的状态和简报摘要：登记在哪些表里、模块外谁在调用哪些函数（调用方属于哪位专家）、哪些全局变量被模块外写入，以及索引核对中有几处问题。即使模型不去读卡片文件，也能看到这些。规则里还写有“熟悉模块”的步骤：Woody、用户或总管让它熟悉模块时，它不改项目代码，先读卡片和 `architecture.md`；再对照源码逐条核对简报，入口函数、模块外的调用方（用 `search_code` 找索引漏掉的、经宏或函数表的调用）、全局变量的写入方都要核对，部分解析、整个解析失败和索引后改过的文件直接读源码；然后按代码记忆技能的顺序追踪流程、参数与存储、谁改参数、数据来源、输出、开关和盲区；把这些写进卡片生成区之后的部分，附上依据（日期、提交、索引时间）；列出索引错了什么、漏了什么及证据，以及看起来属于本模块却不在清单里的文件；最后向总管发一份简短报到。

专家在职责上的要求：报索引问题时要逐个点名，并附上工具结果作为证据，不报没有核对过的数量；熟悉模块时不重建索引。新增对别的模块的调用，或改变别的模块依赖的数据、时序或行为之前，先告诉总管，请对方模块的专家评估，得到答复后再改。改一个值、结构、默认值、地址或函数之前，先全项目搜索用到、构造或复制它的每一处，交接里逐一列出负责人，不能改的副本要指出来。不写“用户已确认”，除非用户真的说过。别的专家转来的请求不算任务，要先交给总管。

专家只改自己负责的文件，以及总管在任务里指定给它的共享文件；需要改别人的文件时停下来，把要改什么、在哪、为什么告诉总管。开工前读自己的功能卡片和 `architecture.md`，并在代码里核实任务依赖的事实（卡片可能过时），索引核对里列为“索引后改过”的文件先重读。接口严格按任务里定的来，行不通时报告阻塞，不擅自改。改完有编译工具就编译，然后更新自己卡片中生成区之后的部分（没有就新建，格式按代码记忆技能里的功能卡片格式，不动生成区，保留“用户更正”一节），再把交接发给总管。

**验证员**不改项目文件。编译；任务说明有硬件或测试环境时跑测试或串口检查；检查合在一起的改动（仓库里用 git diff）：每个改动文件是否归改它的专家或被指定给它、接口两边是否一致（签名、数据布局、NVM 地址、调用顺序）、`#if` 配置分支和任务/调度表顺序是否仍然成立、有没有无关改动。每条问题写明负责的专家、文件和行、严重程度、证据和建议改法；没有问题时给出通过的证据。

所有角色交接都要包含：状态（passed / blocked / changes_requested）、改动文件、提供或使用的接口、证据（命令和实际结果）、未解决问题、是否更新了功能卡片。

## 知识放在哪里

- 专家清单 `.woody/experts.json`、功能卡片 `.woody/features/*.md`、架构文件 `.woody/architecture.md` 都在项目的 `.woody` 文件夹里，跟着项目走。卡片的事实部分由 Woody 在每次索引后重写，讲解部分由专家每次改完后更新。知识都留在卡片里，下一次总管分派和专家开工都能直接用。
- 独立工作区是一个 git worktree，被忽略的 `.woody` 文件夹不会出现在里面。这时规则里写的是所选文件夹 `.woody` 的绝对路径，卡片仍然更新到原项目里。
- 加密电脑上，`experts.json` 由 Woody 写入；读取时先直接读，读到密文再用 PowerShell 7 读明文，与代码记忆配置的读法相同。

## 团队成员的代码记忆

之前团队成员用不了代码记忆：代码记忆的 MCP 要知道项目路径，只有新建对话那条路会把路径传进去，团队成员的 MCP 来自 MCP 列表里的通用条目，没有路径。现在：

- AionCore（woody.13 起）给 aionrs 会话的每个 stdio MCP 加上环境变量 `AIONUI_WORKSPACE`，值是这个会话的工作区；MCP 自己的配置里已经设置了的不覆盖。aionrs 运行在 AionCore 进程内，MCP 继承的是 AionCore 的工作目录，所以只能用环境变量传。
- 代码记忆 MCP 没有收到项目路径时改用 `AIONUI_WORKSPACE`。那个文件夹没开代码记忆时，工具调用返回“该项目未开启代码记忆”。
- 用模板（阶段模板和模块专家）建团队时，团队工作空间开了代码记忆，就给每个角色副本加上代码记忆的 MCP 和技能。没开或检查失败时照常创建团队，只是不带代码记忆。
- 不用模板、直接挑选成员（比如内置电表总管和内置专家）建团队时，Woody 在建团请求里带上 `member_extras`：代码记忆的技能和 MCP（工作空间开了代码记忆时），以及整个团队共用的文件夹。AionCore 把它们写进每个成员对话的 `extra`（`team_member_extras`），技能和 MCP 叠加在成员自己的助手之上；之后加入的成员（界面添加或总管派生）照抄队长的这一份；助手 MCP 重新同步时也保留这些 MCP。实测前这种团队的专家没有 `search_code`，只用 Grep，漏掉了驱动里的定义。

## 团队的文件夹和预加载的专家技能

- 选了工作文件夹的团队有一个自己的文件夹，和单个对话一样放在 `<工作文件夹>/.woody/会话文件/<日期>_<团队名>/{过程,成品}`，按团队名命名，所有成员共用。成员的规则里写明这是团队共用的文件夹，自己建的文件名以自己的名字开头，不依赖队友没告诉自己的文件。实测前团队成员没有文件夹，把中间文件写在项目根目录，别的专家又拿去用。用了独立工作区（worktree）时文件夹仍放在选的那个文件夹里，worktree 删掉也不会丢。
- `woody-module-expert` 技能在 SKILL.md 开头写了 `preload: true`：aionrs 对话把它的全文放进系统提示（技能清单之后，注明技能所在的文件夹），清单里这一条标明“已全文载入”。专家规则改成“按这个技能工作，不用再加载”。代码记忆技能（约 14.4 KB）不预加载，因为它会跟着工作区进入每个对话：专家技能正文开头和专家规则都写明，第一个动作是用 `skills show` 加载它（技能清单里没有就跳过）。验证中发现，专家以前是在加载专家技能的同一条命令里顺带加载它，预加载后这一步没了，它就没人加载。实测前专家在团队任务里常常不加载技能，技能里的规则都没起作用。代价是专家每次对话多约 13.7 KB 系统提示。

## 限制

- 分派、文件归属、确认、返工次数都由模型按规则执行，没有引擎强制。专家改了不属于自己的文件不会被拦住，只会被验证员指出。
- 独立工作区（worktree）没有自己的代码记忆设置时，共用原项目的设置和索引，索引描述的是原项目文件夹。成员在 worktree 里调用 `detect_changes` 时，列出 worktree 相对原项目 HEAD 改动、删除、新增的文件，原项目未提交的改动单独列出，并给出这些文件在索引里的外部调用方；其他工具的结果前加一句说明，提醒改过的文件以 worktree 里的内容为准。
- 专家同时工作时共用一套硬件，烧录和串口验证仍需排队，由总管安排先后。
- 专家副本按团队创建，与阶段模板一样会随团队增多而累积，需要在助手设置里清理。
