# 模块专家团队

按阶段分工的模板（需求 → 设计 → 实现 → 测试 → 评审 → 交付）让同一批角色轮流处理所有模块。固件项目的各个模块往往由不同的人写，逻辑和风格差别很大，更适合按模块分工：一个总管判断需求归谁，每个子模块一位专家长期负责，再由一位验证员检查合在一起的结果。

## 新建团队

工作流模板选“模块专家”，再选基础助手和工作空间。弹窗读取工作空间的 `.woody/experts.json`，列出项目的专家：

- 每位专家有名称、编号、职责和负责的文件。编号用小写字母、数字和 `-`，也是功能卡片 `.woody/features/<编号>.md` 的文件名。负责的文件每行一个，相对项目文件夹；以 `/` 结尾的是文件夹，`*` 匹配一段路径里的任意字符；不能是绝对路径，也不能含 `..`。
- “共享文件”不归任何专家，比如任务表和公共头文件。每次由总管指定一位专家修改。
- 勾选这次加入团队的专家，默认全选。勾选不写回文件。
- 项目还没有 `experts.json` 时，按 `.woody/features` 里已有的功能卡片列出候选，名称先用卡片名，职责和文件待填。没有卡片时列表为空，点“添加专家”逐个添加。
- 任何一位专家的信息不完整或与其他专家重名、重编号时，在该行提示原因，不能创建。最多 12 位专家。

点击“确认创建”：

1. 专家清单有修改或项目还没有文件时，先写入 `.woody/experts.json`。写入失败则提示原因，不创建任何东西。已有文件读不出来（不是合法 JSON、超过 64 KB、加密电脑上 PowerShell 7 也读不出明文）时，提示原因，不覆盖它。
2. 开启“独立工作区”时建 worktree（见 [独立工作区](isolated-workspace.md)）。
3. 以基础助手为模板创建角色副本：总管（队长）、所选专家、验证员，副本命名“团队名 · 角色名”。副本的设置方式与阶段模板相同，见 [工作流角色模板](workflow-presets.md)。
4. 创建团队。

## 三类角色

**总管**的规则里有一张分派表：每位专家的名称、编号、职责和负责的文件，加上共享文件和验证员。文件归属的判定规则写在规则里：路径相同、在以 `/` 结尾的文件夹下、或被 `*` 模式匹配，多条匹配时取最长的那条。总管不改项目文件。收到需求后：

1. 读 `.woody/architecture.md` 和可能相关专家的功能卡片，用代码记忆（没有时用搜索）找到要改的代码，按分派表找到每个文件的负责人。
2. 把分派方案给用户确认：谁做什么、各自改哪些文件、模块之间的接口（函数、数据结构、NVM 地址、调用位置和顺序）、先后顺序、验证员检查什么。用户确认后才派发；用户改了方案要重新确认；用户明确说不用确认时跳过。只问某个模块、不需要改动的问题，直接交给该专家。
3. 用任务派发，任务描述里写完整交接，因为成员看不到总管和其他成员的对话。有接口依赖时先派提供方，拿到它的交接后再派使用方；只有文件不重叠、彼此不依赖时才同时派。不预建任务、不用任务依赖串联，原因同阶段模板。
4. 专家需要改别人的文件时，总管决定由谁改：负责的专家另开任务，共享文件或无人负责的文件指定一位专家。同一个文件不让两位专家同时改。
5. 所有专家交接到齐后，给验证员建一个任务，附上全部交接、改动文件和验收标准。验证员发现问题时，按文件归属交回对应专家，再重新验证；最多两轮，之后把剩余问题报告给用户。
6. 最后汇报：每个模块改了什么、验证证据、遗留问题、更新了哪些功能卡片。

需求不属于任何专家时，总管告诉用户，请用户指定人选或在 `.woody/experts.json` 里加一位专家，不自己动手。

**专家**只改自己负责的文件，以及总管在任务里指定给它的共享文件；需要改别人的文件时停下来，把要改什么、在哪、为什么告诉总管。开工前读自己的功能卡片和 `architecture.md`，并在代码里核实任务依赖的事实（卡片可能过时）。接口严格按任务里定的来，行不通时报告阻塞，不擅自改。改完有编译工具就编译，然后更新自己的功能卡片（没有就新建，格式按代码记忆技能里的功能卡片格式，保留“用户更正”一节），再把交接发给总管。

**验证员**不改项目文件。编译；任务说明有硬件或测试环境时跑测试或串口检查；检查合在一起的改动（仓库里用 git diff）：每个改动文件是否归改它的专家或被指定给它、接口两边是否一致（签名、数据布局、NVM 地址、调用顺序）、`#if` 配置分支和任务/调度表顺序是否仍然成立、有没有无关改动。每条问题写明负责的专家、文件和行、严重程度、证据和建议改法；没有问题时给出通过的证据。

所有角色交接都要包含：状态（passed / blocked / changes_requested）、改动文件、提供或使用的接口、证据（命令和实际结果）、未解决问题、是否更新了功能卡片。

## 知识放在哪里

- 专家清单 `.woody/experts.json`、功能卡片 `.woody/features/*.md`、架构文件 `.woody/architecture.md` 都在项目的 `.woody` 文件夹里，跟着项目走。专家每次改完更新自己的卡片，知识留在卡片里，下一次总管分派和专家开工都能直接用。
- 独立工作区是一个 git worktree，被忽略的 `.woody` 文件夹不会出现在里面。这时规则里写的是所选文件夹 `.woody` 的绝对路径，卡片仍然更新到原项目里。
- 加密电脑上，`experts.json` 由 Woody 写入；读取时先直接读，读到密文再用 PowerShell 7 读明文，与代码记忆配置的读法相同。

## 团队成员的代码记忆

之前团队成员用不了代码记忆：代码记忆的 MCP 要知道项目路径，只有新建对话那条路会把路径传进去，团队成员的 MCP 来自 MCP 列表里的通用条目，没有路径。现在：

- AionCore（woody.13 起）给 aionrs 会话的每个 stdio MCP 加上环境变量 `AIONUI_WORKSPACE`，值是这个会话的工作区；MCP 自己的配置里已经设置了的不覆盖。aionrs 运行在 AionCore 进程内，MCP 继承的是 AionCore 的工作目录，所以只能用环境变量传。
- 代码记忆 MCP 没有收到项目路径时改用 `AIONUI_WORKSPACE`。那个文件夹没开代码记忆时，工具调用返回“该项目未开启代码记忆”。
- 用模板（阶段模板和模块专家）建团队时，团队工作空间开了代码记忆，就给每个角色副本加上代码记忆的 MCP 和技能。没开或检查失败时照常创建团队，只是不带代码记忆。

## 限制

- 分派、文件归属、确认、返工次数都由模型按规则执行，没有引擎强制。专家改了不属于自己的文件不会被拦住，只会被验证员指出。
- 独立工作区（worktree）需要在架构面板里单独开启并索引代码记忆，否则团队成员在 worktree 里用不了代码记忆。
- 专家同时工作时共用一套硬件，烧录和串口验证仍需排队，由总管安排先后。
- 专家副本按团队创建，与阶段模板一样会随团队增多而累积，需要在助手设置里清理。

## 验证

- `tests/unit/renderer/team/Creation/expertRules.test.ts`：角色顺序（总管、专家、验证员），总管规则里的分派表、共享文件、归属判定、确认步骤、先提供方后使用方、不串联任务、两轮返工；专家只改自己的文件、读写自己的卡片、不列出自己；验证员只检查不修改；独立工作区使用绝对知识路径。
- `tests/unit/renderer/team/Creation/moduleExpertsFile.test.ts`：路径规整（反斜杠、`./`、逗号与换行分隔、去重），每类问题的判定，文件的校验与拒绝。
- `tests/unit/codebaseMemory/experts.test.ts`：没有文件时列出功能卡片，写入后格式与读回，读不出的文件不覆盖，无效清单不落盘，密文经明文读取器读取，超过 64 KB 拒绝。
- `tests/unit/renderer/team/Creation/prepareWorkflow.test.ts`、`codebaseMemoryAccess.test.ts`：副本带上代码记忆 MCP 和技能且不重复；只在工作空间开启时提供；失败不阻止建团。
- `tests/unit/renderer/hooks/teamCreateModal.dom.test.tsx`：从已保存清单建团（只勾选的专家加入，不重写文件）；从功能卡片起步，信息不全不能创建，补全后先保存再创建；保存失败不创建任何东西。
- `tests/unit/codebaseMemory/runtimeAdapter.test.ts`：没有项目路径时绑定到 `AIONUI_WORKSPACE`。
- AionCore `factory::aionrs::tests::inject_workspace_env_*`：只给 stdio MCP 加环境变量，不覆盖已有值，没有工作区时不加。
